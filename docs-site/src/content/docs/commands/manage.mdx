All three edit or reload the file you keep in git, so all three treat it
carefully: text surgery rather than re-serialising, verified by re-parsing, and
restored untouched if the result would not load.

## `bedouin add`

```sh
bedouin add apt:ripgrep
bedouin add cargo:zellij@0.40.1
bedouin add brew:fd --no-apply
```

Appends to `packages:` and applies. The version is written quoted, so `1.80`
stays `1.80` rather than becoming the float `1.8`.

## `bedouin remove`

```sh
bedouin remove zellij
bedouin remove rust --language
```

Drops the entry, then applies — which undoes it on this machine: the package is
uninstalled the way it went in, its rc blocks come out, its PATH entries go,
and any file it displaced is given back.

<Aside type="tip" title="Adopted packages">
Removing something that was already on the machine when Bedouin first ran tells
you it will not be uninstalled. Bedouin never removes what it did not install.
</Aside>

Your comments survive. `add` followed by `remove` returns the file
byte-for-byte — there is a test for exactly that, because a tool that reflows
your config is one you stop trusting.

## `bedouin alias` and `bedouin completions`

Discovering that a tool you already have ships a completion generator should
not mean opening a file to write four lines.

```sh
bedouin alias gs='git status'                  # global
bedouin alias z=zellij --package zellij        # scoped to a package
bedouin completions kubectl -- kubectl completion '{{ shell.name }}'
```

The same options ride along on `add`, so a new package arrives complete:

```sh
bedouin add cargo:zellij@0.40.1 \
  --alias z=zellij --alias za='zellij attach' \
  --path '{{ home }}/.cargo/bin' \
  --completions 'zellij setup --dump-completion {{ shell.name }}'
```

`add`'s extras are applied to one text before any of it is written, so a bad
`--alias` leaves nothing half-added.

<Aside type="tip" title="Quoting">
Alias values are quoted on the way in — shell is full of `:` and `#`, and a
bare YAML scalar containing either means something else.

`--completions` splits on whitespace but keeps `{{ … }}` together, since a
naive split turns `{{ shell.name }}` into three arguments. For anything with
real shell syntax, use the `--` form and skip the guessing.
</Aside>

## `bedouin sync`

```sh
bedouin sync
```

Brings the config repository and this machine in step:

1. **Commits local changes** — a batch of edits made with git sync off, or
   anything edited by hand. `.gitignore` is what keeps `.env.bedouin` out.
2. `git pull --rebase`, so your commits land on top of whatever the remote
   gained. A conflict undoes the pull and stops: that one is yours to resolve.
3. Pushes, when the branch has an upstream.
4. Re-plans and shows it. **The plan is the diff.**
5. Asks before applying.

`bedouin sync --skip language/go` leaves a step out, exactly as it does on
[`apply`](/bedouin/commands/plan-apply/#--skip).

## Git sync after every edit

`add`, `remove`, `alias`, `completions`, `absorb` and the web UI each commit
their edit to the config repository and push it. That is on by default, and
does nothing if the config is not a git repository.

To batch several edits into one commit, turn it off, make them, and sync once:

```sh
bedouin sync --auto off
bedouin add apt:jq --no-apply
bedouin add apt:htop --no-apply
bedouin sync                  # one commit, one push, then apply
bedouin sync --auto on
```

The setting lives in the clone's own git config (`bedouin.autosync`), not in
`bedouin.yaml`, so each machine has its own and switching it is not itself a
change to commit.

No credential handling: it uses whatever git setup you already have.
